### Security
- The optional cloud check now turns on only with your own opt-in. A key in `ZN_API_KEY` still does nothing without `ZN_CLOUD=1`, even if the record `zn-gate connect` leaves in `~/.zn/config.json` was written by hand: when that record is what turns the check on, zn-gate uses only the key `connect` saved, only to https://api.usezn.com, and the record must match the saved key (its last four characters). If the key cannot be read, prompts are checked locally and zn-gate says so once.
- The agent hooks: a command that reads the system keychain for zn's entries is checked in linear time (it took several seconds on a 100 KB command before), and `zn-gate connect` and `zn-gate disconnect` now count as commands only the user may run. `POLICY_RULES_VERSION` is `2026-10-17.26`.
- The saved cloud key is also held back while `NODE_OPTIONS` has `--tls-keylog`, `--inspect` (with its variants) or `--openssl-shared-config`, and the zn vault's request tool for agents (`secrets_http_request`) never fills in that key, so an agent cannot use it to revoke the key or spend its quota. The vault does not give the key to the hooks, the secrets broker or `zn run`; a program running as you can still read it, as with any vault or keychain secret, and can use it to analyze text on your quota or revoke it (the key cannot read usage or manage other keys). The hooks also refuse a command that loads zn-gate's own client modules (found by their `zn-gate/lib/client` path) to ask for the key, as a barrier only. `POLICY_RULES_VERSION` is `2026-10-17.26`.
- The saved cloud key is not used while `NODE_DEBUG` is set (Node can print request headers, key included): `connect`, `disconnect` and the cloud check say so in one line and send nothing. `NODE_OPTIONS` options are also recognised when written with underscores (`--tls_keylog`, `--inspect_brk`, `--experimental_loader`), which Node accepts, in the checks of `connect` and `zn audit`. `AUDIT_RULES_VERSION` is `2026-10-17.1`.
